# 三个任务的设计与实验现象

## 1. 任务划分

| 任务 | 函数 | 优先级 | 栈大小 | 周期 | 主要动作 |
|---|---|---:|---:|---|---|
| Task1 | `Task1_LED1` | 4 | 192 OS_STK（768 B） | 1 s | PB0 亮 0.5 s、灭 0.5 s |
| Task2 | `Task2_LED2` | 5 | 192 OS_STK（768 B） | 3 s | PB1 亮 1.5 s、灭 1.5 s |
| Task3 | `Task3_UART` | 6 | 192 OS_STK（768 B） | 2 s | USART1 发送欢迎字符串 |
| Idle | uC/OS-II 内置 | 15 | 128 OS_STK（512 B） | 空闲 | 没有其他任务时运行 |

任务代码在 [../Core/Src/app_tasks.c](../Core/Src/app_tasks.c)，优先级和栈大小在
[../Middlewares/Third_Party/uC-OS2/Cfg/app_cfg.h](../Middlewares/Third_Party/uC-OS2/Cfg/app_cfg.h)。

三个任务都是无限循环，循环体末尾调用 `OSTimeDlyHMSM()` 主动让出 CPU。
等待期间任务不占用 CPU，空闲任务运行；延时到期后，内核在 SysTick 中断里把任务重新
放入就绪表，再由调度器决定是否切换。

---

## 2. 为什么用 `OSTimeDlyHMSM()` 而不是 `HAL_Delay()`

`HAL_Delay()` 是忙等待：CPU 在 `while` 里空转，期间只有中断能打断，低优先级任务
得不到执行。三个任务如果都用 `HAL_Delay()`，就退化成“裸机轮询”，失去 RTOS 的意义。

`OSTimeDlyHMSM()` 会把当前任务从就绪表移除，主动切换到其他任务；延时由 SysTick
节拍驱动。这样：

- LED1 等待时，LED2 和 UART 任务可以运行；
- 所有任务都在等待时，空闲任务运行；
- 每个任务的周期由内核节拍保证，不受其他任务执行时间影响（在 CPU 不超载的前提下）。

## 3. 任务代码

### 3.1 LED1：1 s 完整亮灭周期

```c
static void Task1_LED1(void *p_arg)
{
    (void)p_arg;

    for (;;)
    {
        BSP_LED_On(LED1);
        (void)OSTimeDlyHMSM(0u, 0u, 0u, 500u);

        BSP_LED_Off(LED1);
        (void)OSTimeDlyHMSM(0u, 0u, 0u, 500u);
    }
}
```

亮 500 ms + 灭 500 ms = **1 s 完整周期**。

### 3.2 LED2：3 s 完整亮灭周期

```c
static void Task2_LED2(void *p_arg)
{
    (void)p_arg;

    for (;;)
    {
        BSP_LED_On(LED2);
        (void)OSTimeDlyHMSM(0u, 0u, 1u, 500u);

        BSP_LED_Off(LED2);
        (void)OSTimeDlyHMSM(0u, 0u, 1u, 500u);
    }
}
```

`1 s + 500 ms = 1500 ms`，亮 1.5 s + 灭 1.5 s = **3 s 完整周期**。

### 3.3 UART：每 2 s 发送

```c
static void Task3_UART(void *p_arg)
{
    (void)p_arg;

    for (;;)
    {
        USART1_SendString(UART_MSG);
        (void)OSTimeDlyHMSM(0u, 0u, 2u, 0u);
    }
}
```

`UART_MSG` 用十六进制转义写成 UTF-8 字节，避免 Keil 源文件编码影响发送内容：

```c
static const char UART_MSG[] =
    "hello uc/OS! "
    "\xE6\xAC\xA2"                 /* 欢 */
    "\xE8\xBF\x8E"                 /* 迎 */
    "\xE6\x9D\xA5"                 /* 来 */
    "\xE5\x88\xB0"                 /* 到 */
    "RTOS"
    "\xE5\xA4\x9A"                 /* 多 */
    "\xE4\xBB\xBB"                 /* 任 */
    "\xE5\x8A\xA1"                 /* 务 */
    "\xE7\x8E\xAF"                 /* 环 */
    "\xE5\xA2\x83"                 /* 境 */
    "\xEF\xBC\x81"                 /* ！ */
    "\r\n";
```

> 串口终端必须选择 **UTF-8** 编码，否则中文会显示成乱码。若终端只支持 GBK，
> 需要把上述字节换成 GBK 编码，或者把终端切到 UTF-8。

## 4. 时序

上电后三个任务几乎同时就绪。优先级 4 的 LED1 先运行，然后 LED2，最后 UART，
之后都进入延时。完整时序如下（时间为相对上电时间）：

| 时间 | LED1（PB0） | LED2（PB1） | USART1 |
|---:|---|---|---|
| 0.0 s | 亮 | 亮 | 第 1 条消息 |
| 0.5 s | 灭 | 亮 | — |
| 1.0 s | 亮 | 亮 | — |
| 1.5 s | 灭 | 灭 | — |
| 2.0 s | 亮 | 灭 | 第 2 条消息 |
| 2.5 s | 灭 | 灭 | — |
| 3.0 s | 亮 | 亮 | — |
| 4.0 s | 亮 | 亮 | 第 3 条消息 |
| 4.5 s | 灭 | 灭 | — |
| 6.0 s | 亮 | 亮 | 第 4 条消息 |

用示波器/逻辑分析仪看：

- PB0 方波周期 = 1 s，占空比 50%；
- PB1 方波周期 = 3 s，占空比 50%；
- PA9 上每 2 s 出现一串 115200 的 UART 波形。

## 5. 串口现象

串口助手设置：

```text
波特率   115200
数据位   8
停止位   1
校验     None
流控     None
编码     UTF-8
```

上电后应看到：

```text
===== uC/OS-II V2.92 on STM32F103C8T6 =====
Clock: 72 MHz, Tick: 1 ms, UART: 115200 8N1
LED1=PB0 (1 s), LED2=PB1 (3 s), UART task=2 s

hello uc/OS! 欢迎来到RTOS多任务环境！
hello uc/OS! 欢迎来到RTOS多任务环境！
hello uc/OS! 欢迎来到RTOS多任务环境！
...
```

前 3 行是 `main()` 在启动 OS 之前打印的版本/配置信息；之后每 2 s 一条任务消息。
第一条任务消息在 OS 启动后立即发送，不是等 2 s 后才发。

如果希望“上电后先等 2 s 再发第一条”，把任务改成：

```c
for (;;)
{
    (void)OSTimeDlyHMSM(0u, 0u, 2u, 0u);
    USART1_SendString(UART_MSG);
}
```

## 6. 如何改成“每 1 s 翻转一次”

如果老师对“1 s 周期”的定义是“每 1 s 翻转一次状态”，而不是“完整亮灭周期 1 s”，
只需要改 `app_tasks.c` 里的宏：

```c
#define LED1_HALF_PERIOD_SEC   1u
#define LED1_HALF_PERIOD_MS    0u

#define LED2_HALF_PERIOD_SEC   3u
#define LED2_HALF_PERIOD_MS    0u
```

这样：

- LED1：亮 1 s、灭 1 s，完整周期 2 s；
- LED2：亮 3 s、灭 3 s，完整周期 6 s。

改完后重新编译下载即可。两种实现的“任务周期”分别都是 1 s/3 s，区别只是
“周期”指的是“状态保持时间”还是“完整亮灭周期”。本工程默认采用后者，
与“亮灭周期为 1 s/3 s”的字面含义一致。

## 7. 栈和优先级检查

- 三个任务栈都是 192 个 `OS_STK`，即 768 B；`HAL_UART_Transmit()` 调用层次不深，
  768 B 足够。
- 空闲任务栈 128 个 `OS_STK`，512 B。
- 异常栈 `OS_CPU_ExceptStk` 256 个 `OS_STK`，1 KB。
- 任务优先级 4/5/6 互不相同，避免同优先级时间片轮转；本工程不需要同优先级任务。
- `OS_MAX_TASKS = 8`，足够容纳 3 个应用任务 + 空闲任务；以后加任务不需要改内核，
  只要不超过 8 个。

如果以后在任务里使用 `printf()`、浮点、较大的局部数组，建议把
`APP_TASK_STK_SIZE` 增加到 256 或 320，并重新检查 RAM 占用。
