# 常见问题与调试

## 1. 编译问题

### 1.1 `cannot open source input file "ucos_ii.h"`

原因：Keil 的 Include Paths 没加 `Middlewares/Third_Party/uC-OS2/Source`。

检查：

```text
Options for Target -> C/C++ -> Include Paths
```

应包含：

```text
..\Middlewares\Third_Party\uC-OS2\Source
..\Middlewares\Third_Party\uC-OS2\Cfg
..\Middlewares\Third_Party\uC-OS2\Ports\ARM-Cortex-M3\RealView
```

### 1.2 `OS_CFG.H, Missing ...`

`ucos_ii.h` 会检查 `os_cfg.h` 里是否定义了所有配置项。缺少哪一项，按错误提示补上。
最省事的办法是直接使用本工程的 `os_cfg.h`，它已经包含 V2.92.11 需要的全部宏。

### 1.3 `Undefined symbol OSTaskSwHook`

原因：`os_cpu_a.asm` 的 PendSV 处理里会无条件 `BL OSTaskSwHook`，但
`os_cpu_c.c` 中该函数被 `OS_TASK_SW_HOOK_EN` 条件编译掉了。

解决：

```c
#define OS_TASK_SW_HOOK_EN 1u
```

并在 `os_cpu_c.c` 中保留：

```c
void OSTaskSwHook(void)
{
}
```

### 1.4 `L6200E: Symbol PendSV_Handler multiply defined`

原因：启动文件、C 文件、汇编文件里同时定义了 `PendSV_Handler`。

解决：

- 启动文件里的 `PendSV_Handler` 是 `[WEAK]`，不用删；
- 汇编 `os_cpu_a.asm` 里导出强符号 `PendSV_Handler`；
- **不要**在 `stm32f1xx_it.c` 或其他 C 文件里再定义 `PendSV_Handler`。

### 1.5 `L6915E: Library reports error: __use_no_semihosting was requested`

如果以后在任务里使用 `printf()`，需要重定向 `fputc()` 或关闭半主机。本工程没有使用
`printf()`，不会遇到这个问题。

### 1.6 编译很慢/Objects 很大

Keil 的 `Objects`、`Listings` 是中间文件，可以删掉后重新编译。工程里的
`keilkill.bat` 可以清理。

## 2. 下载问题

### 2.1 ST-Link 找不到芯片

检查：

1. ST-Link 驱动是否安装（Keil 安装目录下有 `STLink` 驱动）。
2. `Options for Target -> Debug -> ST-Link Debugger -> Settings` 是否能识别 SWD。
3. SWDIO 是否接 PA13，SWCLK 是否接 PA14，GND 是否共地。
4. 开发板是否供电（3.3V）。
5. BOOT0 是否为 0。
6. 杜邦线是否接触不良，换短一点的线。

### 2.2 `Flash Download failed - Target DLL has been cancelled`

常见原因：

- 芯片被读保护；
- 下载算法选错；
- 芯片型号不是 C8T6；
- SWD 引脚被程序复用/关闭。

本工程保留 SWD，不会主动关闭调试口。如果之前下载过别的程序把 PA13/PA14 配成普通
GPIO，可以按住复位键，点击下载，再松开复位，让芯片在复位期间被 ST-Link 连接。

### 2.3 下载成功但不运行

- 按一下开发板复位键；
- 确认 BOOT0=0；
- 确认下载的是 `uCOSII_STM32F103.hex` 或 `.axf`，不是旧工程；
- 检查 `SystemClock_Config()` 是否卡在 HSE 启动失败（8 MHz 晶振不起振）。

## 3. 程序跑飞 / HardFault

### 3.1 启动后立刻 HardFault

重点检查：

1. `OS_CPU_ExceptStkBase` 是否在 `OSStart()` 前被赋值。
   本工程在 `OSInitHookBegin()` 中赋值，`OSInit()` 会自动调用它。
2. 任务栈是否 8 字节对齐。`__align(8)` 是否生效。
3. `OSTaskStkInit()` 中 xPSR 是否为 `0x01000000`（Thumb 位）。
4. `PendSV_Handler` 是否确实是汇编里的强符号，而不是启动文件的弱默认死循环。
5. `OSStartHighRdy()` 是否把 MSP 设到了有效的异常栈顶。

### 3.2 只运行一次就死

- 任务函数末尾没有 `for(;;)`，任务返回后进入 `OS_TaskReturn()`；
- 本工程 `OS_TASK_DEL_EN=1`，任务返回会删除自己，不会 HardFault，但也不符合预期；
- 检查所有任务是否都是无限循环。

### 3.3 进入 HardFault 后怎么定位

在 `HardFault_Handler` 里打断点，查看：

```text
LR（EXC_RETURN）
SCB->CFSR
SCB->HFSR
SCB->BFAR
SCB->MMFAR
```

常见 CFSR 位：

- `IMPRECISERR`：总线错误，可能是访问了无效地址；
- `PRECISERR`：精确总线错误，看 BFAR；
- `INVSTATE`：Thumb 位错误，通常是函数指针/栈帧 PC 的 bit0 为 0；
- `UNSTKERR`：异常返回时出栈失败，常见于 PSP 被破坏。

本工程最常见的是“任务栈帧不对”导致 `INVSTATE` 或 `UNSTKERR`。

## 4. LED 问题

### 4.1 LED 不亮

1. LED 极性是否接反：长脚正极，短脚负极。
2. 是否串了电阻，电阻是否虚接。
3. PB0/PB1 是否配置为输出（`MX_GPIO_Init()` 是否被调用）。
4. 程序是否跑起来（串口有没有输出）。
5. 用万用表测 PB0 对 GND：如果一直是 0 V，任务可能没运行；如果一直是 3.3 V，
   可能卡在某个任务里。

### 4.2 LED 常亮

- 任务卡在 `BSP_LED_On()` 之后，没有执行到 `OSTimeDlyHMSM()`；
- 系统节拍没有起来（SysTick 没使能），`OSTimeDlyHMSM()` 永远不返回；
- 检查 `SysTick_Handler()` 是否调用了 `OS_CPU_SysTickHandler()`。

### 4.3 闪烁周期不对

- `OS_TICKS_PER_SEC` 是否为 1000；
- SysTick 是否真的是 1 ms（系统时钟 72 MHz、HAL 初始化正确）；
- `OSTimeDlyHMSM()` 的参数是否写错（秒和毫秒是两个参数）；
- 任务里是否有其他阻塞操作拖长了周期。

本工程：

```c
LED1: 500 ms + 500 ms = 1 s
LED2: 1 s + 500 ms + 1 s + 500 ms = 3 s
```

注意 `OSTimeDlyHMSM(0,0,1,500)` 是 **1.5 s**，不是 1 s + 1.5 s。

## 5. 串口问题

### 5.1 完全没有输出

1. USB-TTL 驱动是否安装，设备管理器是否有 COM 口。
2. 串口助手是否选对 COM 口。
3. 波特率是否 115200，8N1，无校验，无流控。
4. PA9 是否接 USB-TTL 的 **RXD**，PA10 是否接 **TXD**。
5. GND 是否共地。
6. 程序是否运行（LED 是否闪）。
7. USB-TTL 是否是 3.3 V 逻辑；5 V 模块可能无法正确识别 3.3 V TX。

### 5.2 乱码

- 波特率不对；
- 终端编码不是 UTF-8；
- 系统时钟不是 72 MHz，导致实际波特率偏差；
- USB-TTL 晶振/模块质量差；
- 没有共地。

本工程字符串是 UTF-8 字节，串口助手必须选 UTF-8。如果串口助手只有 GBK，
可以把字符串换成 GBK 编码，或者用支持 UTF-8 的终端（如 SSCOM、XCOM、PuTTY、
VS Code Serial Monitor 等，注意选择编码）。

### 5.3 只收到第一条

- 任务卡在 `HAL_UART_Transmit()` 里，检查 `huart1` 初始化和波特率；
- SysTick 没起来，`OSTimeDlyHMSM(0,0,2,0)` 不返回；
- 串口助手开了流控，导致后续数据被阻塞。

### 5.4 中文显示为 `??`

终端不支持 UTF-8，或字体不支持中文。换终端/编码，不是单片机的问题。

## 6. CubeMX 相关问题

### 6.1 打开 `.ioc` 提示版本不匹配

本工程 `.ioc` 由 CubeMX 6.17.0 生成。旧版本 CubeMX 可能提示迁移，按提示迁移即可；
如果不想迁移，直接用本工程已生成的代码，不要重新生成。

### 6.2 点击 GENERATE CODE 后 uC/OS-II 不见了

CubeMX 只生成 HAL 骨架，不知道 uC/OS-II 的存在。它会重写 `main.c`、
`stm32f1xx_it.c` 等文件，并可能重建 Keil 工程分组。

解决：

- 重新生成前备份整个工程；
- 生成后把本工程的 `Core/Src/main.c`、`stm32f1xx_it.c`、`stm32f1xx_hal_msp.c`
  覆盖回去；
- 重新添加 `Middlewares/uC-OS2` 分组和 Include Paths。

### 6.3 没有 `STM32Cube FW_F1 V1.8.7`

在 CubeMX 的 `Help -> Manage embedded software packages` 中安装 F1 包。
如果安装的是更新版本，生成代码可能有细微差异，但 HAL API 基本兼容。

## 7. 其他

### 7.1 为什么不用 TIM4 做节拍？

可以用 TIM4，但本工程用 SysTick 更简单：

- HAL 已经配置 SysTick 为 1 ms；
- SysTick 是 Cortex-M3 内核定时器，移植层可以直接使用；
- 不需要额外占用一个 TIM。

### 7.2 为什么 SysTick 和 PendSV 都是优先级 15？

PendSV 必须最低，保证上下文切换在所有中断处理完之后进行。SysTick 也放最低，
避免它打断 PendSV。uC/OS-II 的临界区用 PRIMASK 关中断，所以节拍中断不会在
临界区里丢失。

### 7.3 为什么任务栈要 8 字节对齐？

Cortex-M3 的异常帧要求栈 8 字节对齐。`OSTaskStkInit()` 里会把栈顶向下对齐到 8 字节，
任务栈数组也用 `__align(8)`。如果不对齐，异常返回时可能 HardFault。

### 7.4 可以在任务里用 `HAL_Delay()` 吗？

可以编译，但不推荐。`HAL_Delay()` 是忙等待，会浪费 CPU，并且阻塞同优先级/低优先级
任务。RTOS 任务应使用 `OSTimeDly()`/`OSTimeDlyHMSM()` 让出 CPU。

### 7.5 可以加信号量/队列吗？

可以。把 `os_cfg.h` 中对应的 `OS_SEM_EN`、`OS_Q_EN` 等改为 1，增加
`OS_MAX_EVENTS`，然后在任务里使用 `OSSemCreate()`、`OSSemPend()`、`OSSemPost()` 等。
本工程为了保持简单，全部关闭了。
