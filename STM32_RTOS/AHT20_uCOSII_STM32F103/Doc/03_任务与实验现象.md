# 三个任务与实验现象（AHT20 版本）

## 1. 任务表

| 任务 | 优先级 | 栈大小 | 周期 | 行为 |
|---|---:|---:|---|---|
| Task1_LED1 | 4 | 256 OS_STK（1 KB） | 1 s | PB0 亮 0.5 s、灭 0.5 s |
| Task2_LED2 | 5 | 256 OS_STK（1 KB） | 3 s | PB1 亮 1.5 s、灭 1.5 s |
| Task3_AHT20 | 6 | 256 OS_STK（1 KB） | 2 s | 触发 AHT20、等 80 ms、读 7 字节、串口打印 |
| Idle | 15 | 128 OS_STK（512 B） | — | 空闲任务 |

栈从任务一的 192 增加到 256，因为 AHT20 任务调用了 `snprintf()`，需要更多栈空间。

## 2. Task3 流程

```text
每 2 s 一次：
  │
  ├─ 如果 g_aht20_ready == 0：AHT20_Init()
  │
  ├─ AHT20_StartMeasurement()
  │     0x70 + AC 33 00
  │
  ├─ OSTimeDlyHMSM(0,0,0,80)
  │     等待转换，同时让出 CPU
  │
  ├─ AHT20_ReadMeasurement()
  │     0x71 + 7 字节
  │
  ├─ 换算 T/RH，检查 CRC
  │
  ├─ USART1 打印
  │
  └─ 用 OSTimeGet() 计算剩余时间，补足 2 s
```

关键代码：

```c
start = OSTimeGet();

if (g_aht20_ready == 0u)
{
    (void)AHT20_Init();
}

if (AHT20_StartMeasurement() != 0u)
{
    (void)OSTimeDlyHMSM(0u, 0u, 0u, 80u);
    if (AHT20_ReadMeasurement(&data) != 0u)
    {
        /* 格式化并发送 */
    }
}

elapsed = OSTimeGet() - start;
if (elapsed < 2000u)
{
    (void)OSTimeDly((INT16U)(2000u - elapsed));
}
```

为什么要用 `OSTimeGet()`：

- `OSTimeDlyHMSM(..., 80)` 已经消耗 80 ms；
- 如果读完后直接再延时 2 s，实际周期会变成 2.08 s；
- 用 `OSTimeGet()` 算出已经花掉的时间，只补剩余部分，周期严格为 2 s。

## 3. 输出格式

```c
T=%s C, RH=%s %%RH  [status=0x%02X CRC=%s]
```

例如：

```text
T=26.45 C, RH=58.32 %RH  [status=0x18 CRC=OK]
```

- `T`：温度，摄氏度，两位小数；
- `RH`：相对湿度，%RH，两位小数；
- `status`：AHT20 读出的状态字节，正常常见 `0x18`（CAL=1，BUSY=0）；
- `CRC`：`OK` 或 `ERR`。

没有使用 `printf("%f")`，而是把浮点数转成两位定点字符串，避免引入庞大的浮点格式化库。
转换函数：

```c
static void FixedToStr(char *buf, size_t size, float value)
{
    int32_t scaled;
    ...
    (void)snprintf(buf, size, "%s%d.%02d", negative ? "-" : "", whole, frac);
}
```

## 4. 完整串口现象

上电后：

```text
===== uC/OS-II V2.92 + AHT20 on STM32F103C8T6 =====
Clock: 72 MHz, Tick: 1 ms, UART: 115200 8N1
LED1=PB0 (1 s), LED2=PB1 (3 s), AHT20 task=2 s
AHT20: SCL=PB6, SDA=PB7, 7-bit addr=0x38
AHT20 init: OK (addr 0x38, init cmd BE 08 00)

T=26.45 C, RH=58.32 %RH  [status=0x18 CRC=OK]
T=26.47 C, RH=58.30 %RH  [status=0x18 CRC=OK]
T=26.46 C, RH=58.35 %RH  [status=0x18 CRC=OK]
...
```

时间关系：

| 时间 | 现象 |
|---:|---|
| 0 ms | 系统启动，AHT20 初始化（约 40 ms） |
| ~40 ms | OSStart，三个任务开始 |
| ~120 ms | 第一条温湿度输出（触发后等 80 ms） |
| ~2.12 s | 第二条 |
| ~4.12 s | 第三条 |

LED1 仍然每 0.5 s 翻转，LED2 每 1.5 s 翻转，不受 AHT20 的 80 ms 等待影响，
因为 Task3 在等待时调用了 `OSTimeDlyHMSM()`，CPU 让给了 LED 任务和空闲任务。

## 5. 故障输出

### 5.1 初始化失败

```text
AHT20 init: FAIL (check wiring/pull-ups)
AHT20 init failed: check PB6/PB7 and 0x38
```

可能原因：

- AHT20 没接 3.3V/GND；
- SCL/SDA 接反；
- 模块没有上拉电阻；
- 地址不是 0x38（少数兼容模块可能不同）；
- PB6/PB7 被其他外设占用。

### 5.2 触发 NACK

```text
AHT20 trigger NACK at 0x70
```

说明地址字节或命令字节没有收到 ACK。通常是接线/上拉/电源问题。

### 5.3 读取失败

```text
AHT20 read failed (busy/NACK)
```

可能是 80 ms 等待不够、总线受干扰、CRC/状态异常。程序会在 20 ms 后重试一次。

### 5.4 CRC 错误

```text
T=26.45 C, RH=58.32 %RH  [status=0x18 CRC=ERR]
```

数据仍然打印出来，但 CRC 不匹配。优先检查：

- SCL/SDA 上拉电阻；
- 杜邦线是否过长；
- 是否有其他 I2C 设备干扰；
- 软件 I2C 延时是否被中断打断得太厉害。

## 6. 与任务一的区别

| 项目 | 任务一 | 任务二 |
|---|---|---|
| Task3 | 每 2 s 发固定字符串 | 每 2 s 读 AHT20 并发送温湿度 |
| 新增外设 | 无 | PB6/PB7 软件 I2C + AHT20 |
| 新增文件 | 无 | `i2c_soft.c/h`、`aht20.c/h` |
| 任务栈 | 192 | 256 |
| 串口内容 | `hello uc/OS! ...` | `T=..., RH=...` |
| LED 任务 | PB0 1 s、PB1 3 s | 不变 |

任务一的 uC/OS-II 移植层、SysTick 1 ms、PendSV 切换、LED 任务全部保留。
